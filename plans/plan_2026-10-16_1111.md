## Context
- **Money engine:** `executeTransfer` is the shared code that moves USD between two users in one atomic step, with an optional hook that settles a linked document in the same step. Withdrawals use the same "hold the money now, return it if it fails" pattern I'll reuse.
- **Accounts and access:** USD-only wallets, `requireMoneyMover` (sign-in, 2FA, KYC, limits, and now the frozen check), admin flag on the login token, `audit()`, monthly stats and in-app notifications.
- **Dev conventions:** emulator-only "dev" buttons stand in for anything that can't run locally; `smoke.mjs` is the end-to-end test and vitest covers invariants.
- **Constraint:** pages must not read `new Date()` during render (this Next version rejects it at build time).

## Design decisions (my assumptions)
1. **Real KYC (Stripe Identity)**
   - `startKyc` creates a Stripe Identity check (document plus selfie) and returns Stripe's hosted page.
   - The existing Stripe webhook also handles `identity.verification_session.*`: verified sets KYC verified at tier 1, and needing more input or a failure sets rejected with the reason.
   - Tier 2 stays an admin action (a new "set tier" button).
   - Locally there's a dev "Simulate verified/rejected" button; the old `devVerifyKyc` stays.
2. **Email notifications**
   - A Firestore trigger on new `notifications` documents emails the user, respecting a per-user `emailNotifications` setting the user can change in Settings.
   - Invoices sent to people without an account are emailed directly.
   - Provider is **Resend** (one HTTPS call, secret `RESEND_API_KEY`). Without a key, or locally, emails go to a `mailOutbox` collection plus the log, so you can still see them.
3. **Multi-currency**
   - USD stays the main wallet; sending, requests, invoices, withdrawals, checkout and limits all stay USD.
   - New per-currency balances are stored as `balances/{uid}_{CUR}`, with their own ledger entries.
   - `convert` moves money between your own currencies at the latest stored rate, minus a 0.5% spread shown before you confirm. It refuses rates older than 24 hours and records the rate used on each ledger entry.
4. **Savings goals**
   - Goals are stored as `pots/{id}` (name, target, balance). Moving money between the wallet and a goal is one atomic step with `savings_in`/`savings_out` ledger entries.
   - Money in a goal can't be spent; you have to move it back first.
   - A goal can only be deleted when it's empty.
5. **Merchant checkout**
   - **Merchant profile:** a user turns on merchant mode in `/merchant` (business name, webhook URL).
   - **API keys:** shown once, and only a hashed copy is stored (`apiKeys/{sha256}`).
   - **Public API** (`api`): `POST /v1/checkouts` and `GET /v1/checkouts/:id`, authenticated with a Bearer API key.
   - **Hosted payment page:** `/checkout?id=` lets a signed-in FastPay user pay through the existing money engine with a settle hook. Each checkout can only be paid once.
   - **Webhooks:** `checkout.paid` is signed with HMAC-SHA256 using a per-merchant secret. Deliveries are queued in `webhookDeliveries` and retried with backoff (up to 6 tries) by a scheduled job.
   - The merchant dashboard lists checkouts, keys (create/revoke) and delivery attempts.
6. **Fraud rules** (checked before every P2P send)
   - **The rules:**
     - Velocity: more than 5 sends in 10 minutes.
     - New account: more than $200 within 24 hours of signing up.
     - Large send to a new recipient: more than $500 to someone you've never paid.
     - Recipient frozen.
   - **Outcomes:**
     - A rule can block the send outright (velocity, frozen recipient).
     - Or it can **hold** it: the money is taken from the sender into `holds/{id}`, and the recipient isn't paid yet.
   - **Admin review:** admins see a new queue to approve (pays the recipient) or reject (refunds the sender). Each decision happens once and is audited.
   - The thresholds live in one config object so they're easy to tune.

## Implementation steps
1. **Shared changes:** types, input checks (server and client), new ledger types, the stats helper, and rules and indexes for all the new collections.
2. **KYC:** `kyc.ts` plus the webhook branch, a Settings/KYC banner flow, and the admin "set tier" action.
3. **Email:** `email.ts` with the trigger and Resend sender, the outbox, the Settings toggle, and the invoice email.
4. **Multi-currency:** `fx.ts` gets `convert`, a `/currencies` page, and a balance card showing your other currencies.
5. **Savings goals:** `pots.ts` and a `/savings` page.
6. **Merchant:** `merchant.ts` (profile, keys, the HTTP API, payment, webhook queue and job), plus the `/merchant` and `/checkout` pages.
7. **Fraud:** `risk.ts`, wired into the `transfer` callable, plus the admin review queue; the Send page explains when a payment is "held for review".
8. **Nav and Settings:** add entries under "More".
9. **Tests:** vitest for conversion conserving value and refusing stale rates, goal deposits/withdrawals, a hold being decided only once, and checkout being paid only once; `smoke.mjs` checks for every new function, rule and the public API, including webhook signature checks against a local receiver.
