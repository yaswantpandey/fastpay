- **Shared money-moving code:** `executeTransfer(db, input, hook?)` does the atomic debit and credit, and an optional hook settles a linked document (request or invoice) in the same step. New features will reuse it.
- **Server check before money moves:** `requireMoneyMover` confirms the user is signed in, has 2FA and is KYC-verified, and applies their limits.
- **Patterns:** pages are client components built with shadcn Card/Button/Input and `httpsCallable`; scheduled jobs get a dev-only button because they don't run on the emulator; `smoke.mjs` is the end-to-end test.
- **New dependency:** only `qrcode` (for QR images). Charts will be plain CSS/SVG bars, with no chart library.

## Design decisions (my assumptions — tell me if you want something different)
1. **Withdraw:**
   - The real path is Stripe Connect Express: you link a bank via Stripe's own setup flow, then the server sends the money with `transfers.create`. That needs Connect turned on in your Stripe account.
   - On the local emulators, a "dev payout" mode lets you mark a payout paid or failed by hand.
   - The money is taken from the wallet the moment you request a withdrawal and logged as a pending `payout`. If the bank payout fails, a matching `refund` entry gives it back.
2. **Admins:** an admin is marked by a flag on their login token (`admin: true`), set with a one-off script (`functions/scripts/make-admin.mjs`). The server checks that flag, never the browser.
3. **Freeze:** `users.frozen=true`. The server check before any money movement refuses a frozen user.
4. **Reverse a transfer:** the admin's reversal is recorded as a new transfer marked "reversal", with `refund` ledger entries for both users. If the recipient has already spent the money, it's refused rather than letting their balance go negative.
5. **Spending insights:**
   - Monthly in/out totals are kept up to date on the server inside the same step that moves the money, stored as `stats/{uid}_{YYYY-MM}`.
   - Category tags: users may set only a `category` field on their own ledger entries, enforced by the rules. Amounts and balances stay read-only.
6. **Recurring payments:**
   - Schedules are stored as `schedules/{id}`. A job every 15 minutes runs whatever is due through `executeTransfer`.
   - Each run gets its own repeat-proof key (`sched_{id}_{runNo}`), so a retried run never pays twice.
   - A schedule pauses itself after 3 failures in a row. There's a dev "Run due now" button.
7. **Split bills:** this creates one payment request per person, all tagged with a shared `splitId`. Paying uses the existing request flow, and progress is worked out from those requests, with no separate tracking.
8. **Contacts and QR:**
   - Saved contacts live at `users/{uid}/contacts/{id}` and the user can edit their own, with rules checking the fields.
   - "Recent" contacts come from people in your ledger.
   - The pay link is `/pay?to=<email>&amount=<optional>`, and the QR code just encodes that link.
